# ADR-014: Platform Session Lease and Fencing Model

**Status:** Accepted.  
**Date:** 2026-08-26.

## Context

A future worker may need exclusive responsibility for a platform-allocated session. At-least-once command delivery and process crashes make a simple Boolean owner flag unsafe. Phase 1 must establish durable lease reclamation and stale-owner fencing before any worker lifecycle integration is trusted.

## Decision

Phase 1 stores one lease row per platform session in PostgreSQL. A claim creates or replaces an expired lease using a transaction and row-level locking. Each successful claim increments the session’s monotonic `generation`, generates a new opaque UUID lease token, stores the claimant `owner_id`, and records `lease_expires_at`. Renewal and owner-state updates must predicate on `session_id`, `owner_id`, lease token, generation, and a non-expired lease. A stale token/generation is rejected; an expired lease may be reclaimed by another owner.

The model is explicitly **at least once**, not exactly once. A crashed allocator can leave a durable session before returning a response, and redelivery returns that session. A future worker must present the current fence tuple for any authoritative route/ownership change.

## Alternatives Considered

| Alternative | Outcome |
|---|---|
| Redis lock/lease | Rejected; no measured need and it introduces unavailable Phase-1 infrastructure. |
| Database advisory locks only | Rejected; they do not preserve durable observable lease generation/token metadata across the lifecycle. |
| Timestamp-only ownership | Rejected; it cannot fence an old owner that resumes after expiry. |
| Exactly-once allocation/delivery claim | Rejected; the source contract is at least once; durable idempotency and fencing are the honest guarantee. |

## Consequences

PostgreSQL serializes ownership changes and tests can prove races with actual transactions. The current application still does not launch workers; lease APIs demonstrate the future safety boundary only. Owner IDs are opaque service identities in Phase 1 and are not user identities or client credentials.

## Security Considerations

Lease tokens are high-entropy opaque values generated by the platform and are never written to human-facing error responses or diagnostics. Inputs validate non-empty bounded owner IDs; SQL predicates prevent a stale owner from mutating current ownership. No client-supplied tenant ID or lease token creates authorization by itself.

## Scaling Trigger

Revisit when measured lease contention, connection pool saturation, or multi-region/session-placement requirements exceed PostgreSQL’s proven operational envelope.

## Revisit Trigger

Revisit before worker launch, worker-route dispatch, service identity issuance, or any platform API that exposes session status outside an internal trust boundary.
